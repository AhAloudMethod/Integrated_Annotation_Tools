# アノテーションツールの使い方を説明する

相手はプログラミングをしない人である．画面で何を押せばよいかを，画面の言葉で答える．このツールのコードと README は直さない．

## 1. 答える前に決める 2 つ

- **画面**：通常の画面か実験モードか．実験モードでは参加者に「設定」などが見えず，できる操作が変わる．
- **相手の役**：実験者（準備する人），評価者・分析者（動画を評価する人），発声者（録画して本人が評価する人）のどれか．

質問から決まらず，答えが変わるときだけ 1 つ聞く．変わらないなら，よくある場合で答え，冒頭に「通常の画面での手順である」のように前提を 1 行書く．

## 2. 根拠を探す順

1. `index.html`：ボタン・設定の欄の文言と `title`（ツールチップ），「？」の説明パネル．画面の言葉はここから取る．README に無い機能（「読み込む」など）もここで見つかる．
2. `README.md`：下の表の節を見出しで Grep して，その節だけを読む．全体は読まない．
3. `core/*.js`・`modes/*.js`：README に書かれていない挙動を確かめるときだけ読む．

| 質問の種類 | README の節 |
|---|---|
| 再生・戻す・取り消し・上書き | 再生と書き込み，1 フレーム移動，グラフの時間軸のズーム |
| 区間ごとに止めて入れる | 聴いてから入力 |
| 評価する範囲・区切り | 評価区間，グラフでの直接編集 |
| 声が無い所 | 発声なし（0），発声なしを事前に設定する（実験モード），表示と画面の配置（発声の区間） |
| ゲームパッド・スライダー | コントローラー（ゲームパッド） |
| 声で入れる | 音声入力 |
| 方式の違い・選び方 | 原典の仕様と改変点の対応表，カスタム方式 |
| 実験の準備と当日 | 実験モード（実験フォルダ，進め方，録画の試行） |
| 結果のファイル・列 | 書き出しファイル，書き出し形式（CSV の列） |

## 3. 回答の形

1. 結論を 1〜2 文で書く（できるか，どこを押すか）．
2. 手順を番号つきで書く．ボタンと欄は「設定」→「コントローラー」のように「」で示し，キーは Space，Ctrl+Z のように書く．
3. 間違えやすい点を 1〜3 個書く（実験モードでは効かない，上書きされる，など）．
4. 該当があれば，最後に「画面で確かめていない点」の欄を置き，下の 2 つに当たる記述をすべて挙げる．

内部の名前の扱い：

- 操作ログの type，`meta.*`，`core/` のファイル名，`localStorage` のキーは書かない．相手が解析のために聞いたときだけ書く．
- CSV のファイル名と列名は，結果のファイルを聞かれたときに書く．
- `npm run …`・`node tools/…` のようにコマンドや JSON の編集が要る作業は，手順として渡さない．「その設定は Claude が書ける」と申し出るか，experiment-config skill で行う．

README と `index.html` に書かれていないことは，手順 4 の欄に入れる．次の 2 つがこれに当たる．

- コードを読んで推し量った挙動
- Grep で見つからなかったことから「その機能は無い」とした判断

## 4. 説明資料を頼まれたとき

1. 読み手の役（評価する人か，実験を組む人か）と，使う画面（通常か実験モードか）を決める．依頼から決まらなければ聞く．
2. explainer-doc-html skill で HTML にする．
3. 構成はこの順にする：何ができるか → 開き方 → 画面の見方 → 1 本の動画を評価する手順 →（実験を組む人なら）実験モード → 書き出されるファイル → つまずきやすい点．読み手の役に要らない節は入れない．
4. 開発の話（テスト，方式の足し方，名前空間，ファームウェアの書き込み）は入れない．

作業中に見つけた README と実物の食い違い（版の番号，無いファイルなど）は資料に書かず，渡すときのメッセージでユーザに伝える．

## 文体

回答も資料も，である調で書く（「押す．」「できる．」）．相手が利用者でも，です・ます調にしない．句読点は「，」「．」を使う（japanese-writing-style の核）．
